# 05. API 명세서

> API 개발 및 테스트 시 참조. 클라이언트 → Gateway → 서비스 헤더 흐름 확인.

---

## 공통 사항

### Base URL

```
http://{SERVER_URL}/api/v1
```

### 인증

- JWT Bearer 토큰 방식 사용
- 로그인 성공 시 발급된 토큰을 `Authorization: Bearer {token}` 헤더에 포함
- API Gateway에서 토큰 검증 후 각 서비스로 라우팅
- 검증된 사용자 정보(`X-User-Id`, `X-User-Role`)는 Gateway가 헤더로 전달

### 클라이언트 → Gateway 헤더

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| Authorization | String | 필수 (GUEST 제외) | Bearer {JWT} |
| Content-Type | String | 필수 (Body 있을 때) | application/json |

### Gateway → 각 서비스 (자동 주입)

| 필드 | 타입 | 설명 |
|---|---|---|
| X-User-Id | String | JWT에서 추출한 userId |
| X-User-Role | String | JWT에서 추출한 role (USER / ADMIN) |

### 공통 규칙

- 페이지네이션: `size` 파라미터는 10, 30, 50만 허용 (그 외 기본 10건)
- 정렬: 기본 `createdAt` DESC (생성일순)
- 모든 엔드포인트는 매 요청 시 JWT payload 기반 DB 권한 재검증 수행

### 회원가입

**POST** `/api/v1/users/signup`

**Request Header**

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| Content-Type | String | 필수 | application/json |

**Request Body**

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| email | String | 필수 | 이메일 |
| password | String | 필수 | 비밀번호 |

**Response 201**

```json
{
  "success": true,
  "status": 201,
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "userId": "uuid",
    "email": "test@test.com",
    "nickname": "닉네임",
    "role": "USER"
  }
}
```

**Response 400 (유효성 실패)**

```json
{
  "success": false,
  "status": 400,
  "message": "입력값이 올바르지 않아요.",
  "errors": [
    { "field": "email", "message": "이메일 형식이 올바르지 않아요." }
  ]
}
```

**Response 409 (이메일 중복)**

```json
{

  "status": 409,
  "message": "이미 사용 중인 이메일이에요.",
```

### 선착순 진입

**POST** `/api/v1/drops/{dropId}/purchase`

> Redis에서 재고를 원자적으로 선점하고 즉시 202를 반환한다. Kafka 발행(`purchase.confirmed`)은 비동기 워커가 처리하며, 발행 최종 실패 시 hold TTL(기본 10분) 자연 보상.

**Path Variable**

| 파라미터 | 타입 | 설명 |
|---|---|---|
| dropId | UUID | 진입할 드롭 ID |

**Response 202** (선점 성공)

```json
{
  "success": true,
  "status": 202,
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "orderId": "uuid",
    "queueNumber": 42
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| orderId | UUID | Drop 도메인이 생성한 주문 ID. Order 서비스가 `purchase.confirmed`를 컨슘해 동일 ID로 주문 생성 |
| queueNumber | Long | 대기 순번 (1부터 시작, `queue:{dropId}` INCR 반환값) |

**에러 코드 (선착순 진입)**

| 코드 | HTTP | 설명 |
|---|---|---|
| DROP-001 | 404 | 드롭을 찾을 수 없음 |
| DROP-002 | 409 | 드롭이 OPEN 상태가 아님 |
| DROP-004 | 409 | 재고 소진 (SOLD_OUT) |
| DROP-005 | 409 | 이미 구매 신청한 드롭 (DUPLICATE_PURCHASE) |

## Notification Service API

### 엔드포인트 목록

| Method | URL | 기능 | 권한 |
|---|---|---|---|
| GET | `/api/v1/notifications` | 내 알림 목록 조회 | USER, ADMIN |
| PATCH | `/api/v1/notifications/{notificationId}/read` | 알림 읽음 처리 | USER, ADMIN |

> slackId 조회는 notification-service가 user-service 내부 API(`GET /internal/v1/users/{userId}/slack`)를 Feign으로 호출한다. notification-service가 직접 노출하는 엔드포인트 아님.
