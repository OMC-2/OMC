# 01. 비즈니스 정책 & SAGA 흐름

> 기능 구현 전 반드시 확인. 재고/환불/쿠폰/주문 상태 전이 정책이 헷갈릴 때 참조

---

## 드롭 방식 2가지

| | Drop (선착순) | Raffle (추첨) |
|---|---|---|
| **방식** | 오픈 순간 선착순 즉시 구매 | 응모 기간(가승인) → 추첨 → 당첨자 결제 |
| **결제 시점** | 구매 즉시 선결제 | 당첨 확정 후 자동 결제 |
| **동시성 제어** | Redis 재고 차감 (원자적 Lua Script) | Redis Set 중복 방지 (`SADD`) |
| **레퍼런스** | 나이키 Line | 나이키 Draw |

## 서비스 기능 정의 (MVP)

### User Service
- 회원가입 / 로그인
- JWT 기반 인증
- ROLE_USER / ROLE_ADMIN 권한 분리

### Product Service
- 상품 등록 / 수정 / 삭제 (관리자), 목록/상세 조회
- 재고 스냅샷 조회 (드롭 오픈 시 totalQty 제공)
- 재고 확정 차감: `payment.completed` 이벤트 수신 후 DB 반영 (`@Version` 낙관적 락)
- 재고 수동 수정 (관리자): Redis 동기화 포함

### Drop Service
- 드롭 생성 (관리자) — 시작/종료 시간 설정
- 드롭 오픈 스케줄링 (`@Scheduled`)
- 드롭 상태 관리: `SCHEDULED → OPEN → CLOSED`
- Kafka 이벤트 발행: `drop.opened`, `drop.closed`
- 재고 선점 (Redis Lua Script, TTL 10분)

### Raffle Service
- 래플 생성 (관리자)
- 응모 접수, Redis Set 기반 중복 응모 방지
- 드롭 종료 후 추첨 실행
- 당첨자 선정 → Kafka 이벤트: `raffle.winner.selected`

### Order Service
- 주문 생성 (INSTANT: 사용자 직접 / RAFFLE: 당첨 이벤트 수신 후 자동)
- 주문 상태 관리 (아래 상태 전이 참조)
- 10분 결제 실패 시 자동 취소 (Scheduler + Redis TTL)
- Outbox 패턴으로 이벤트 발행 보장
- RDBMS 기반 DLQ로 분산 장애 모니터링

### Payment Service
- 결제 요청 / PG사 연동
- 결제 성공 / 실패 처리
- 환불 처리 (Drop: 익일 자정까지)
- SAGA 패턴 기반 분산 트랜잭션 참여

### Coupon Service
- 선착순 쿠폰 발급, 중복 발급 방지
- 쿠폰 생성 및 관리 (할인율/할인액/유효기간/발급 수량)
- 주문서 내 가용 쿠폰 목록 조회 및 최종 할인 금액 계산
- 주문 결제 시 실시간 사용, 정책에 따라 복구/소멸 처리

### Notification Service
- 드롭 오픈 알림
- 래플 당첨 / 낙첨 알림
- 주문 완료 알림
- 결제 실패 / 환불 완료 알림
- Kafka Consumer 기반 비동기 처리

## 재고 차감 정책

### Drop (선착순) — 2단계

```
구매 요청
→ Drop Service: Redis 재고 선점 (Lua Script, 원자적) + TTL 10분 시작
→ 선점 성공: 202 즉시 반환 → Kafka purchase.confirmed 발행
→ Order Service: 주문 생성 (Kafka 비동기)
→ 결제 완료: Product Service가 DB 재고 확정 차감 (@Version 낙관적 락)
→ 결제 실패 / TTL 만료: Drop Service가 Redis 선점 해제 (재고 복구)
```

| 항목 | 내용 |
|---|---|
| 선점 방식 | Redis Decrement (Lua Script로 원자적 처리) |
| 선점 TTL | 10분 (만료 시 자동 선점 해제, 재고 복구) |
| 확정 차감 시점 | `payment.completed` 이벤트 수신 후 DB 차감 |
| 재고 복구 조건 | 결제 실패 / TTL 만료 / 주문 취소 (SAGA 보상 트랜잭션) |
| 환불 시 재고 복구 | **없음 (소멸)** — 한정판 희소성 유지 |

### Raffle (추첨) — 즉시 확정

```
응모 (결제 수단 가승인 및 빌링키 등록)
→ 재고 선점 없음 (응모 기간 중 재고 건드리지 않음)
→ 추첨 실행 (당첨자 선정)
→ 당첨자: 빌링키로 자동 결제 진행 → 결제 성공 시 DB 재고 확정 차감
→ 결제 실패 시: 당첨 즉시 취소 및 예비 당첨자 추첨 (또는 재고 소멸)
→ 낙첨자: 결제 발생 안 함 (환불 불필요) → 쿠폰 복구 없음
```

| 항목 | 내용 |
|---|---|
| 선점 시점 | **없음** — 추첨 후 당첨자에 한해 즉시 확정 차감 |
| 확정 차감 시점 | 결제 확정(당첨 확정) 이후 |
| 재고 복구 조건 | 없음 — 낙첨자는 결제만 환불, 재고는 당첨자 수만큼만 차감 |
| 환불 시 재고 복구 | 없음 (소멸) |

## 환불 정책

### Drop (선착순)

- **환불 가능 기간**: 구매 완료 다음날 자정 (23:59:59) 까지
  - 예: 06/20 10:05 구매 → 06/21 23:59:59 까지 환불 가능

| 조건 | 환불 가능 여부 | 판정 방식 |
|---|---|---|
| 익일 자정 이내 요청 | ✅ 가능 | `created_at` 기준 다음 날 자정 이전 + `CONFIRMED` 상태 |
| 익일 자정 초과 요청 | ❌ 불가 | 예외 발생 |
| `CONFIRMED` 이전 상태 | ❌ 불가 | `PENDING_PAYMENT`, `PAID` 상태에서 환불 차단 |
| `SHIPPING` 이후 | ❌ 불가 | 스케줄러에 의해 전환된 경우 무조건 차단 |
| `DELIVERED` 이후 | ❌ 불가 | |

**환불 시 처리:**
```
결제 취소 (PG사 환불 API)
→ 재고 소멸 (복구 없음)
→ 쿠폰 소멸 (복구 없음)
→ 주문 상태 → REFUNDED
→ 환불 완료 알림 발송
```

> 단, 결제 실패 및 10분 타임아웃에 의한 자동 취소 시에는 재고와 쿠폰이 복구됩니다.

### Raffle (추첨)

- **당첨 후 환불 불가** (나이키 SNKRS 동일 정책)

| 케이스 | 처리 |
|---|---|
| 결제 실패 | 주문 취소 (환불 아님, 결제 안 됐으므로) |
| 응모 미결제 시 | 주문 자동 취소 |
| 플랫폼 귀책 사유 | 전액 환불 (관리자 수동 처리) |

## 쿠폰 정책

| 항목 | 내용 |
|---|---|
| 적용 시점 | 결제 요청 직전 (주문서 생성 및 확인 단계) |
| 적용 한도 | **1주문 1쿠폰** (중복 적용 불가) |
| 만료 처리 | `expires_at` 만료 시 지연 평가(Lazy Evaluation)로 자동 사용 불가 처리 |
| 소수점 처리 | 10원 단위 버림 |

**복구/소멸 기준:**

| 상황 | 쿠폰 처리 |
|---|---|
| 결제 실패 / 시스템 타임아웃 | ✅ 정상 복구 (재사용 가능) |
| 래플 낙첨 | ❌ 영구 소멸 |
| 단순 변심 환불 | ❌ 영구 소멸 |

### MVP 검증용 쿠폰 3종

| 쿠폰명 | 적용 대상 | 할인 방식 | 스펙 | 검증 목적 |
|---|---|---|---|---|
| 기습 오프닝 선착순 쿠폰 | `DROP_ONLY` | `FIXED_AMOUNT` | 5,000원 할인 | 선착순 발급 트래픽 방어 + 드롭 결제 실패 시 롤백 테스트 |
| 래플 응모자 전용 쿠폰 | `RAFFLE_ONLY` | `PERCENTAGE` | 10% 할인 (최대 20,000원 한도) | 최대 할인 한도 로직 + 래플 낙첨 시 쿠폰 소멸 정책 테스트 |
| 첫 가입 웰컴 쿠폰 | `COMMON` | `FIXED_AMOUNT` | 10,000원 할인 | 범용 할인 로직 + 최소 주문 금액 검증 |

## 주문 상태 전이

### 상태 정의

| 상태 코드 | 설명 | 진입 시점 | 종류 |
|---|---|---|---|
| `PENDING_PAYMENT` | 주문 가생성, 결제 대기 | 드롭 `purchase.confirmed` 수신 시 | 진행 |
| `PAID` | 결제 완료, 재고 확정 차감 대기 | `payment.completed` 수신 시 | 진행 |
| `CONFIRMED` | 주문 확정 (재고 확정 차감 완료) | 드롭 `stock.deducted` / 래플 `raffle.winner.selected` 수신 시 | 진행 |
| `SHIPPING` | 배송 시작 | 배송 스케줄러 | 진행 |
| `DELIVERED` | 배송 완료 | 배송 스케줄러 | **종단** |
| `CANCELLED` | 주문 취소 | 타임아웃 / 결제 실패 / 재고 차감 실패 | **종단** |
| `REFUND_REQUESTED` | 환불 요청 접수, PG 취소 진행 중 | 유저 환불 요청 (`CONFIRMED`에서만) | 진행 |
| `REFUNDED` | 환불 완료 | PG 환불 완료 | **종단** |

> 종단 상태(`DELIVERED`, `CANCELLED`, `REFUNDED`)는 이후 어떤 트리거가 와도 전이되지 않습니다.

### INSTANT (드롭) 전이 흐름

```
PENDING_PAYMENT → PAID → CONFIRMED → SHIPPING → DELIVERED
       │            │          │
       │            │          └─ (익일 자정 내 요청) → REFUND_REQUESTED → REFUNDED
       │            └─ (재고 차감 실패 Case B, 자동 환불) → CANCELLED
       └─ (재고 선점 TTL 10분 만료 / 결제 실패) → CANCELLED
```

### RAFFLE (래플) 전이 흐름

```
(당첨 후 결제 성공 시) CONFIRMED → SHIPPING → DELIVERED
   · 당첨자: 자동 결제 성공 상태 → CONFIRMED 직행, 이후 환불 불가
   · 결제 실패: 당첨 즉시 취소 (주문 CANCELLED 또는 미생성)
   · 낙첨자: 주문 미생성 (결제 없음)
   · 예외: 플랫폼 귀책 시 관리자 수동 전액 환불
```

### 상태 전이 규칙 표

| From | To | 트리거 | 주문 유형 |
|---|---|---|---|
| (None) | `PENDING_PAYMENT` | `purchase.confirmed` 수신 | INSTANT |
| (None) | `CONFIRMED` | `raffle.winner.selected` 수신 | RAFFLE |
| `PENDING_PAYMENT` | `PAID` | `payment.completed` 수신 | INSTANT |
| `PENDING_PAYMENT` | `CANCELLED` | `hold.expired` (10분 타임아웃) / `payment.failed` | INSTANT |
| `PAID` | `CONFIRMED` | `stock.deducted` 수신 | INSTANT |
| `PAID` | `CANCELLED` | `stock.failed` 수신 (Case B, 자동 환불 동반) | INSTANT |
| `CONFIRMED` | `SHIPPING` | INSTANT: `now > refundable_until` / RAFFLE: `now > confirmed_at + 1h` | 공통 |
| `SHIPPING` | `DELIVERED` | 배송 스케줄러 (시간 경과) | 공통 |
| `CONFIRMED` | `REFUND_REQUESTED` | 유저 환불 요청 + Double Check + 환불 윈도우 통과 | INSTANT |
| `REFUND_REQUESTED` | `REFUNDED` | PG 결제 취소 완료 | INSTANT |

> 이 표에 없는 전이는 전부 불가. RAFFLE은 CONFIRMED 이후 환불·취소 전이 없음.

### 배송 스케줄러 기준

| 유형 | 전이 조건 | 목적 |
|---|---|---|
| **INSTANT (드롭)** | `now() > refundable_until` | 환불 마감(익일 자정) 경과 후에만 배송 시작 |
| **RAFFLE (래플)** | `now() > confirmed_at + 1시간` | 환불 불가이므로 확정 1시간 후 즉시 배송 |

### 상태 검증 원칙

| 원칙 | 내용 |
|---|---|
| 단방향 전이 보장 | 역방향 전이 시도 시 `IllegalStateException` 발생 |
| 단계 건너뛰기 차단 | 반드시 정해진 이전 상태를 거쳐야 다음 상태로 이동 |
| 배송 상태 제어 통제 | `CONFIRMED` 이후 배송 상태는 내부 스케줄러만 변경 가능 |
| 종단 상태 불변성 | `CANCELLED`/`REFUNDED` 상태에서 강제 전이 차단, 늦게 도착한 이벤트는 무시(no-op) |
| 동시성 경합 방어 | 환불 요청 vs 배송 스케줄러 충돌 → Redisson 분산 락 + Double Check |

## 주문/환불/쿠폰 통합 예외 정책 (Rollback)

| 상황 | 재고 처리 | 쿠폰 처리 | 사유 |
|---|---|---|---|
| 고객 단순 변심 환불 (드롭, 익일 자정 내) | ❌ 영구 소멸 | ❌ 영구 소멸 | 한정판 희소성 유지 + 악성 어뷰징 차단 |
| 결제 실패 / 타임아웃 (Case A) | ✅ 정상 복구 (drop-service 내부 처리) | ✅ 정상 복구 (`coupon.restored` 발행) | 시스템 귀책 또는 단순 노쇼 |
| 결제 후 재고 차감 실패 (Case B) | 해당 없음 (차감된 재고 없음) | ✅ 정상 복구 (`coupon.restored` 발행) | 시스템 귀책 → 자동 환불 + 쿠폰 복구 |
| 만료 후 결제 (LATE_PAYMENT) | 해당 없음 (타임아웃 시 이미 복구) | 해당 없음 (타임아웃 시 이미 복구) | 주문 `CANCELLED` 유지, 뒤늦은 결제만 자동 환불 |
| 래플 낙첨 | 해당 없음 | ❌ 영구 소멸 | 쿠폰은 '추첨권 구매'에 소진된 것으로 간주 |

## SAGA 패턴 흐름

### 5.1 Happy Path (정상 흐름)

```
purchase.confirmed  (Drop Service: Redis 재고 선점 완료)
→ order.created     (Order Service: 주문 생성)
→ payment.completed
→ stock.deducted    (Product Service: DB 확정 차감)
→ order.confirmed
```

### 5.2 Case A — 10분 미결제 / 결제 실패

**타임아웃 경로:**
```
purchase.confirmed
→ drop-service: TTL 만료 감지 → Redis 복구(ZREM+INCR+SREM) → hold.expired 발행
→ order-service: hold.expired 수신 → 주문 CANCELLED → coupon.restored 발행
→ coupon-service: coupon.restored 수신 → 쿠폰 복구
```

**결제 실패 경로:**
```
purchase.confirmed
→ payment-service: payment.failed 발행
→ drop-service: payment.failed 수신 → Redis 복구 (내부 처리)
→ order-service: payment.failed 수신 → 주문 CANCELLED → coupon.restored 발행
→ coupon-service: coupon.restored 수신 → 쿠폰 복구
```

> 재고 복구: Redis 키를 소유한 **drop-service가 내부 처리** (별도 이벤트 없음)
> 쿠폰 복구: **order-service가 `coupon.restored` 발행** → coupon-service 수행

### 5.3 Case B — 결제 후 재고 차감 실패

```
payment.completed
→ stock.failed
→ refund.done       (자동 환불)
→ coupon.restored   (쿠폰 복구)
→ order.cancelled
```

- order-service: `stock.failed` 수신 → `CANCELLED` → `coupon.restored` 발행

### 5.4 Case C — 쿠폰 이중 사용 실패

- 쿠폰 검증/사용 실패는 payment 트랜잭션 내 발생 → `payment.failed`로 수렴 → **5.2 Case A와 동일 처리**

### 5.5 사용자 직접 환불 (단순 변심)

```
refund.requested → refund.done → order.cancelled
```

> 재고 복구 및 쿠폰 복구 이벤트 발행 없음 — 소멸

### 5.6 래플 낙첨 처리 (환불 없음)

```
raffle.loser.notified 발행
→ 낙첨 알림톡 발송
→ (선결제가 없으므로 환불 처리 없음)
→ coupon.restored 없음  (낙첨 시 쿠폰 소멸 정책)
```

### 5.7 LATE_PAYMENT (만료 후 결제)

```
hold TTL 만료 → 주문 CANCELLED  (5.2 타임아웃 경로 완료)
→ (뒤늦게) payment.completed 도착
→ drop-service: ZREM 시도 → 결과 0 감지(키 이미 만료) → LATE_PAYMENT 판정 → refund.requested 발행
→ payment-service: refund.requested 수신 → 자동 환불
→ order-service: payment.completed 수신 시 주문이 이미 CANCELLED → no-op (종단 상태 불변성)
```

> LATE_PAYMENT 판정 주체: **drop-service** (Redis 선점 키 보유)
> order-service는 Redis 조회 없이 "종단 상태면 무시" 방어 로직만 수행

## 분산 환경 고가용성 정책

### Transactional Outbox 패턴

- **목적**: Kafka 브로커 장애 시에도 주문 데이터와 이벤트 발행 간 최종 일관성 보장
- **동작**: 주문 트랜잭션 내에서 ORDERS + OUTBOX_EVENTS 동시 저장 (로컬 트랜잭션)
- **배치**: 0.5초 주기 스케줄러가 `INIT` 상태 레코드 Kafka 발행 → ACK 받으면 `PUBLISHED`
- **실패 처리**: 재시도 3회 초과 시 `FAILED` → 자동 스캔 제외 → 관리자 수동 재발행 API

### 분산 락 경계

```
[Redisson 분산 락 획득]
→ [@Transactional 시작]
→ [주문 및 Outbox 저장]
→ [트랜잭션 커밋]
→ [분산 락 해제]
```

> 락이 트랜잭션을 완전히 감싸야 함 — 커밋 전 락 해제 시 찰나의 중복 주문 발생 가능

### RDBMS 결합형 DLQ

- **목적**: 컨슈머 측 처리 실패 시 데이터 유실 방지 (Outbox FAILED와 발생 지점 다름)
- **흐름**: 컨슈머 예외 → 최대 재시도 초과 → 카프카 DLQ 토픽 발행 + `FAILED_EVENT_LOGS` 테이블 기록
- **복구**: 관리자 API로 `original_payload`를 원본 토픽 재투입 → ACK 받으면 `RESOLVED`
