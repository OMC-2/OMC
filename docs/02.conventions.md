# 02. 개발 컨벤션

> 코드 리뷰 기준이 되는 문서. 모든 팀원이 숙지 후 개발 시작.

---

## 1. Git 브랜치 전략

```
main          ← 배포 브랜치. 직접 push 금지
develop       ← 통합 브랜치. feature 브랜치를 여기로 merge
feature/{...} ← 기능 개발 브랜치
hotfix/{...}  ← 긴급 수정 브랜치 (main에서 분기)
```

### 브랜치 네이밍

```
feature/user-signup
feature/drop-crud
feature/gateway-jwt-filter
hotfix/user-auth-null-pointer
```

### 규칙

- `main`에 직접 push 금지. PR만 허용
- `develop` → `main` merge
- 기능 단위로 브랜치를 나눕니다. 하나의 브랜치에 여러 기능을 섞지 않습니다
- 브랜치 이름은 kebab-case, 소문자

## 2. 커밋 메시지

### 형식

```
<type>: <subject>

[optional body]
```

### type 목록

| type | 설명 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `chore` | 빌드 설정, 의존성, 설정 파일 변경 |
| `docs` | 문서 작성/수정 |
| `test` | 테스트 코드 추가/수정 |
| `style` | 코드 포맷, 세미콜론 등 로직 변화 없는 스타일 변경 |

### 예시

```
feat: 회원가입 API 구현
feat: 가입 승인/거절 API 구현
fix: 승인 시 Keycloak 호출 NPE 수정
chore: user-service build.gradle 의존성 추가
docs: user-service API 명세 업데이트
refactor: UserService 트랜잭션 범위 분리
```

### 규칙

- 제목은 50자 이내, 마침표 없음
- 현재형으로 작성 (`구현`, `수정`, `추가`)
- 본문은 필요할 때만. `왜` 변경했는지를 씁니다

## 3. PR 규칙

### PR 제목

커밋 메시지와 동일한 형식 사용:

```
feat: 회원가입 API 구현
feat: drop-service CRUD 전체 구현
fix: 배송 상태 업데이트 동시성 오류 수정
```

### PR 작성 기준

- PR 하나는 기능 하나. 리뷰어가 30분 내에 리뷰할 수 있는 크기를 유지합니다
- `develop` 브랜치로 PR을 올립니다
- 셀프 머지 금지. 최소 2명의 Approve 후 머지합니다
- 리뷰 요청 후 24시간 내 리뷰를 목표로 합니다

## 4. 패키지 구조

모든 서비스는 4계층 구조를 따릅니다. 패키지 루트는 `com.omc.{service-name}` 입니다.

```
com.omc.{service-name}
├── presentation/
│   ├── controller/
│   └── dto/
│       ├── request/
│       └── response/
├── application/
│   ├── service/              ← 비즈니스 로직 (유스케이스)
│   ├── scheduler/            ← @Scheduled (드롭 오픈/종료, hold 만료, 배송 등)
│   └── event/
│       ├── producer/         ← 이벤트 발행 (application이 "무엇을" 발행할지)
│       └── consumer/         ← 이벤트 수신 핸들러 (수신 후 유스케이스 호출)
├── domain/
│   ├── entity/
│   ├── repository/           ← JPA Repository 인터페이스 (구현 없음)
│   ├── exception/            ← ErrorCode enum, 도메인 예외
│   └── vo/                   ← 값 객체 (선택, 금액·상태 등)
└── infrastructure/
    ├── persistence/          ← Repository 구현 / QueryDSL (필요 시)
    ├── redis/                ← RedisTemplate, Lua Script (drop만 비중 큼)
    ├── kafka/                ← KafkaTemplate 설정, 직렬화, 실제 send/listen 어댑터
    ├── client/               ← FeignClient
    └── config/               ← @Configuration
```

### 서비스별 패키지 루트

| 서비스 | 패키지 루트 |
|---|---|
| `user-service` | `com.omc.user` |
| `drop-service` | `com.omc.drop` |
| `order-service` | `com.omc.order` |
| `product-service` | `com.omc.product` |
| `payment-service` | `com.omc.payment` |

## 6. API 응답 형식

모든 응답은 `common` 모듈의 `ApiResponse<T>` 사용. **`ResponseEntity` 직접 반환 또는 `Map` 반환 금지.**

### 성공 응답

```java
// 200 OK (데이터 있음)
return ResponseEntity.ok(ApiResponse.success(data));

// 200 OK (데이터 없음)
return ResponseEntity.ok(ApiResponse.ok());

// 201 Created
return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.created(data));
```

### 실패 응답

구체적인 예외 클래스를 `throw` — `GlobalExceptionHandler`가 자동으로 `ApiResponse`로 변환:

```java
throw new UserNotFoundException();
throw new UserAlreadyExistsException();
```

### 응답 JSON 구조

**성공:**
```json
{
  "success": true,
  "status": 200,
  "message": "OK",
  "data": { ... }
}
```

**실패:**
```json
{
  "success": false,
  "status": 404,
  "errorCode": "USER-001",
  "message": "사용자를 찾을 수 없습니다.",
  "data": null
}
```

**Validation 실패:**
```json
{
  "success": false,
  "status": 400,
  "errorCode": "COMMON-001",
  "message": "잘못된 입력값입니다.",
  "data": [
    { "field": "username", "value": "a", "reason": "4자 이상 입력해야 합니다." }
  ]
}
```

## 8. 예외 처리

### 기본 구조

`common` 모듈의 `BusinessException`을 상속해서 **에러 코드마다 구체적인 예외 클래스**를 만듭니다.

```java
// domain/exception/ 에 위치
public class UserNotFoundException extends BusinessException {
    public UserNotFoundException() {
        super(UserErrorCode.USER_NOT_FOUND);
    }
}
```

### throw 방법

```java
// ❌ RuntimeException 직접 사용
throw new RuntimeException("사용자를 찾을 수 없습니다.");

// ❌ BusinessException에 ErrorCode 직접 넘기기
throw new BusinessException(UserErrorCode.USER_NOT_FOUND);

// ✅ 구체적인 예외 클래스 사용
throw new UserNotFoundException();
```

### 예외 클래스 파일 위치

```
domain/exception/
├── UserErrorCode.java
├── UserNotFoundException.java
├── UserAlreadyExistsException.java
└── InvalidApprovalStatusException.java
```

### 규칙 요약

- `BusinessException` 직접 throw 금지 — 반드시 구체적인 서브클래스 사용
- `try-catch`로 잡아서 응답을 직접 만들지 않습니다 (`GlobalExceptionHandler`가 처리)
- `RuntimeException` 직접 throw 금지
- Feign 호출 실패는 `FeignErrorDecoder`에서 구체적인 예외 클래스로 변환

### 권한 체크

`GatewayHeaderAuthFilter`(`common` 모듈)가 `X-User-Role` 헤더를 읽어 `SecurityContext`에 세팅.
각 서비스는 JWT를 파싱하지 않으며, `@PreAuthorize`로 선언적으로 권한 검증:

```java
@PreAuthorize("hasRole('ADMIN')")
@PatchMapping("/api/v1/products/{productId}")
public ResponseEntity<ApiResponse<ProductResponse>> update(...) { ... }

// 복수 권한
@PreAuthorize("hasAnyRole('ADMIN', 'USER')")
```

```java
// SecurityConfig — @EnableWebSecurity, @EnableMethodSecurity 선언 불필요 (common이 처리)
@Configuration
public class SecurityConfig {

    @Value("${gateway.secret}")
    private String gatewaySecret;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/actuator/**", "/swagger-ui/**", "/v3/api-docs/**").permitAll()
                .anyRequest().authenticated()
            )
            .addFilterBefore(new GatewayHeaderAuthFilter(gatewaySecret), UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

> **참고**: SecurityConfig를 정의하지 않은 서비스는 `common`의 `GatewaySecurityAutoConfiguration`이 fallback `SecurityFilterChain`을 자동 적용합니다. fallback은 `/swagger-ui/**`, `/v3/api-docs/**`, `/actuator/**`만 허용하고 나머지는 인증을 요구합니다. 본인 서비스에 권한 제어가 필요하면 위 예시처럼 직접 SecurityConfig를 작성하세요.

### 현재 사용자 ID 획득

`@AuthenticationPrincipal`이나 `@RequestHeader`로 userId를 받지 않습니다. `SecurityUtil`을 사용하며, **용도에 따라 호출 위치가 다릅니다:**

| 용도 | 위치 | 이유 |
|---|---|---|
| userId가 비즈니스 식별자 ("누구의 데이터") | 컨트롤러 | 어드민이 타 유저 데이터를 조회하는 등 재사용 가능성 |
| userId가 감사 목적 (`deletedBy` 등) | 서비스 | "현재 로그인한 사람이 한 행위"라는 의도를 서비스가 직접 표현 |

```java
// ✅ 비즈니스 식별자 — 컨트롤러에서 꺼내 파라미터로 전달
@GetMapping("/me")
public ResponseEntity<ApiResponse<UserProfileResponse>> getMyProfile() {
    UUID userId = SecurityUtil.getCurrentUserId()
            .orElseThrow(UnauthorizedException::new);
    return ResponseEntity.ok(ApiResponse.success(userService.getProfile(userId)));
}

// ✅ 감사 목적 — 서비스에서 직접 호출
public void delete(UUID dropId) {
    UUID deletedBy = SecurityUtil.getCurrentUserId()
            .orElseThrow(UnauthorizedException::new);
    ...
}
```

`createdBy` / `updatedBy`는 `BaseEntity`의 JPA Auditing(`@CreatedBy`, `@LastModifiedBy`)이 자동 처리합니다. 서비스에 `JpaConfig`(`@EnableJpaAuditing` + `AuditorAwareImpl` 빈)가 필요합니다.

## 9. Gateway 헤더 스펙

Gateway가 JWT 검증 후 각 서비스로 주입하는 헤더. **각 서비스는 이 헤더를 신뢰하고 JWT를 별도로 파싱하지 않습니다.**

| 헤더 | 타입 | 설명 | 예시 |
|---|---|---|---|
| `X-User-Id` | `String` (UUID) | 인증된 사용자 UUID | `6f7d9c5e-7fa3-...` |
| `X-Username` | `String` | 로그인 ID | `user01` |
| `X-User-Role` | `String` | 현재 사용자 권한 | `USER`, `ADMIN` |
| `X-User-Status` | `String` | 현재 사용자 승인 상태 | `APPROVED` |

### 인증 불필요 엔드포인트 (Gateway 통과)

```
POST /api/v1/users/signup
GET  /actuator/**
```

### 서비스 간 Feign 호출 시

`FeignHeaderPropagationInterceptor`가 모든 Feign 요청에 게이트웨이 헤더를 자동 전파. `@RequestHeader` 직접 선언 불필요:

```java
// ✅ @RequestHeader 선언 불필요 — 자동 전파
@FeignClient(name = "user-service")
public interface UserFeignClient {
    @GetMapping("/internal/v1/users/{userId}")
    ApiResponse<InternalUserResponse> getUser(@PathVariable UUID userId);
}
```

## 10. Swagger API 문서화

### 접속

Gateway를 통해 모든 서비스 API를 한 곳에서 확인합니다.

```
http://localhost:8080/swagger-ui.html
```

상단 드롭다운에서 서비스를 선택하면 해당 서비스의 API 목록이 표시됩니다.

### 각 서비스 담당자가 해야 할 작업

컨트롤러에 아래 어노테이션을 추가하면 Swagger UI에 반영됩니다.

```java
@Tag(name = "User", description = "회원 API")
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    @Operation(summary = "회원가입")
    @PostMapping("/signup")
    public ResponseEntity<ApiResponse<SignupResponse>> signup(@RequestBody SignupRequest request) { ... }
}
```

| 어노테이션 | 위치 | 설명 |
|---|---|---|
| `@Tag` | 컨트롤러 클래스 | Swagger UI 좌측 그룹명 |
| `@Operation` | 메서드 | API 제목 |

### "Try it out" 사용 시

1. Keycloak에서 Access Token 발급 (`POST /api/v1/users/login`)
2. Swagger UI 우측 상단 자물쇠 버튼(Authorize) 클릭
3. `BearerAuth` 항목에 발급받은 Access Token 입력
4. 이후 인증이 필요한 API를 직접 호출 가능

## 11. DB 컨벤션

### 테이블 네이밍

- 모든 테이블은 `p_` 접두사 + snake_case **복수형**
- 예: `p_users`, `p_drops`, `p_order_items`

### PK

- 모든 PK는 **UUID v7**, 컬럼명은 `{테이블단수명}_id`
- 예: `user_id`, `drop_id`, `order_id`

### Audit 필드 (6개 필수)

모든 테이블에 아래 6개 필드를 포함합니다. `BaseEntity` 상속 시 자동으로 채워집니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `created_at` | `TIMESTAMP NOT NULL` | 생성 일시 (자동) |
| `created_by` | `VARCHAR(100)` | 생성자 ID |
| `updated_at` | `TIMESTAMP` | 수정 일시 (자동) |
| `updated_by` | `VARCHAR(100)` | 수정자 ID |
| `deleted_at` | `TIMESTAMP` | 논리 삭제 일시 |
| `deleted_by` | `VARCHAR(100)` | 논리 삭제자 ID |

### Soft Delete

- 물리 삭제(`DELETE` SQL) 금지
- 삭제 시 `deleted_at = now()`, `deleted_by = {요청자 ID}` 세팅
- 모든 엔티티에 `@SQLRestriction("deleted_at IS NULL")` 선언 필수 (Hibernate 6.x)
- **주의**: Native Query 사용 시에는 직접 `deleted_at IS NULL` 조건을 추가해야 합니다

```java
// ✅ 전역 필터 적용으로 접미사 불필요
userRepository.findById(userId)
    .orElseThrow(UserNotFoundException::new);
```

### 스키마 분리

각 서비스는 자신의 스키마만 접근. 다른 서비스의 테이블에 직접 쿼리 금지:

```yaml
# application.yaml (user-service 예시)
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/omc?currentSchema=user_db
```

## 12. 서비스 구현 규칙

### 레이어 책임

| 레이어 | 책임 | 금지 사항 |
|---|---|---|
| `Controller` | HTTP 요청/응답, 헤더 추출, 권한 체크 | 비즈니스 로직, DTO 변환 |
| `Service` | 비즈니스 로직, DTO 변환, 트랜잭션 관리 | HTTP 관련 코드 (`HttpServletRequest` 등) |
| `Repository` | DB 접근 | 비즈니스 로직 |
| `Entity` | 도메인 상태, 상태 변경 메서드 | 외부 의존성 |

### DTO 변환 위치

DTO 변환은 **Service에서** 합니다. Controller는 요청을 받아 Service를 호출하고 응답을 반환하는 역할만:

```java
// Service — DTO 변환 후 반환
public SignupResponse signup(SignupRequest request) {
    User user = userRepository.save(...);
    return SignupResponse.from(user);
}

// Controller — 얇게 유지
return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.created(userService.signup(request)));
```

### 트랜잭션

- Service 클래스 레벨에 `@Transactional(readOnly = true)` 기본 선언
- 쓰기 메서드만 `@Transactional`로 오버라이드

```java
@Service
@Transactional(readOnly = true)
public class UserService {

    @Transactional
    public ApproveResponse approve(UUID userId) {
        User user = userRepository.findById(userId)
            .orElseThrow(UserNotFoundException::new);
        user.approve();                      // 도메인 검증 먼저
        keycloakService.enableUser(userId);  // 검증 통과 후 외부 호출
        return ApproveResponse.from(user);
    }

    public UserResponse getUser(UUID userId) { ... }  // readOnly 자동 적용
}
```

### 엔티티 상태 변경

상태 변경 로직은 Service가 아닌 **엔티티 메서드**로 캡슐화:

```java
// ❌ Service에서 직접 세팅
user.setStatus(UserStatus.APPROVED);

// ✅ 엔티티 메서드 위임
user.approve();
```

## 13. 엔티티 생성 규칙

- **외부**: 정적 팩토리 메서드 `create()` 사용 필수
- **내부**: `@Builder`를 `private` 생성자에 선언 — `create()` 안에서만 사용 (클래스 레벨 선언 금지)
- **JPA**: `@NoArgsConstructor(access = AccessLevel.PROTECTED)` 필수

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class User extends BaseEntity {

    @Builder(access = AccessLevel.PRIVATE)
    private User(UUID userId, String username, UserStatus status) {
        this.userId = userId;
        this.username = username;
        this.status = status;
    }

    // 외부에서 유일한 생성 진입점
    public static User create(UUID userId, String username) {
        return User.builder()
                .userId(userId)
                .username(username)
                .status(UserStatus.PENDING)  // 초기값 고정
                .build();
    }
}
```

## 15. 서비스 간 통신

### 규칙

- 서비스 간 통신은 **`OpenFeign`만 사용**
- 다른 서비스의 모듈을 `implementation project(':...')`로 의존 금지
- `common` 모듈만 각 서비스가 `implementation`으로 의존 가능
- FeignClient는 `infrastructure/client/` 패키지에 위치

### Feign 호출 실패 처리

`CommonFeignErrorDecoder`가 자동 등록되어 Feign 오류를 `RemoteServiceException`으로 변환. 서비스 코드에서 Feign 예외를 직접 `catch` 불필요:

| 상황 | 에러 코드 |
|---|---|
| 응답 body 파싱 성공 | 원격 서비스의 에러 코드 그대로 전달 |
| 응답 body 없음 | `COMMON-998` |
| 응답 body 파싱 실패 | `COMMON-999` |

### Feign 호출 예시

```java
// ✅ @RequestHeader 선언 불필요 — FeignHeaderPropagationInterceptor가 자동 전파
@FeignClient(name = "product-service")
public interface ProductFeignClient {
    @PostMapping("/internal/v1/inventories/{productId}/deduct")
    ApiResponse<Void> deductStock(
        @PathVariable UUID productId,
        @RequestBody DeductStockRequest request
    );
}
```
