# 10. 모니터링 가이드

> Prometheus / Grafana / Zipkin / Sentry 구성 및 사용법. 로컬 환경 기준.

---

## 모니터링 스택 구성

```
[각 서비스]
  │  /actuator/prometheus  ← 메트릭 노출
  ▼
[Prometheus]  ← 15초마다 메트릭 수집
  │
  ▼
[Grafana]     ← 대시보드 시각화 (Prometheus 데이터 소스)

[각 서비스]
  │  HTTP 요청/응답 시 자동으로 스팬 전송
  ▼
[Zipkin]      ← 분산 트레이싱 수집 및 시각화 (로컬 컨테이너)

[각 서비스]
  │  예외 발생 시 Sentry SDK가 자동으로 이벤트 전송
  ▼
[Sentry Cloud]  ← 에러 추적 및 Slack 알림 (soldout.sentry.io)
```

## Zipkin

### 트레이스 조회 방법

1. http://localhost:19411 접속
2. 상단 검색 필터에서 `+` 버튼 클릭
3. `serviceName` 선택 → `gateway` 입력
4. **Run Query** 클릭

> Zipkin 3.x부터 서비스 드롭다운이 제거됨. 필터 방식으로 조회해야 한다.

### 트레이스 읽는 법

검색 결과에서 각 행이 **요청 1건**이다.

```
Root gateway: post /api/v1/coupons/xxx/issue   11 spans   200ms
```

- **Root 이름** → 게이트웨이가 받은 HTTP 메서드 + 실제 경로
- **spans** → 이 요청에서 생성된 전체 스팬 수 (게이트웨이 + 다운스트림 서비스 합산)
- 클릭하면 워터폴 형태로 각 서비스 간 호출 흐름 확인 가능

### 트레이스 검색 예시

쿠폰 발급 요청만 보고 싶을 때:
1. `+` → `http.url` → `/api/v1/coupons` 입력 후 Run Query

특정 서비스 전체 요청:
1. `+` → `serviceName` → `coupon-service`

## Gateway 포트 구조

게이트웨이는 하나의 프로세스지만 **포트를 2개** 사용한다.

```
게이트웨이 컨테이너
├── 포트 8080  ← API 서버 (클라이언트 요청 처리, Zipkin 트레이싱 됨)
│   └── /api/v1/**
│
└── 포트 8081  ← Management 서버 (운영 도구 전용, Zipkin 트레이싱 안 됨)
    └── /actuator/health   ← Docker healthcheck
    └── /actuator/prometheus  ← Prometheus scraping
```

`management.server.port: 8081`로 Spring Boot의 management server를 분리했다.

**이유**: actuator 엔드포인트(`/actuator/health`, `/actuator/prometheus`)가 초당 수회씩 호출되면 Zipkin에 노이즈가 쌓인다. Management server를 별도 포트로 분리하고 해당 포트의 HTTP 관측을 `ObservationPredicate`로 차단하면 actuator 트레이스가 Zipkin에 기록되지 않는다.

> 다른 서비스(user-service, coupon-service 등)는 포트 분리를 하지 않아서 actuator 트레이스가 Zipkin에 보일 수 있다. 게이트웨이가 모든 요청의 진입점이라 노이즈가 특히 심해서 게이트웨이만 적용했다.

## 샘플링 설정

모든 서비스 `application.yml`에서 환경변수로 샘플링 비율을 제어한다.

```yaml
management:
  tracing:
    sampling:
      probability: ${TRACING_SAMPLING_PROBABILITY:1.0}
```

기본값 `1.0` (100%) — 환경변수를 지정하지 않으면 모든 요청이 Zipkin에 기록된다.

### 대량 트래픽 테스트(JMeter 등) 시 주의사항

> **반드시 샘플링 비율을 낮추고 테스트해야 한다.**

Zipkin이 메모리 256MB 제한(`JAVA_OPTS: -Xmx256m`)으로 실행 중이기 때문에,
100% 샘플링 상태에서 대량 트래픽을 보내면 Zipkin이 OOM으로 죽거나 트레이스가 유실된다.

**테스트 시작 전에 `TRACING_SAMPLING_PROBABILITY=0.1` 로 설정하고 서비스를 재시작한다.**

```bash
# 전체 서비스를 0.1 샘플링으로 재시작
TRACING_SAMPLING_PROBABILITY=0.1 docker compose \
  -f docker-compose.yml \
  -f docker-compose.services.yml \
  up -d
```

특정 서비스만 바꾸고 싶을 때:

```bash
TRACING_SAMPLING_PROBABILITY=0.1 docker compose \
  -f docker-compose.yml \
  -f docker-compose.services.yml \
  up -d coupon-service gateway
```

테스트가 끝나면 기본값(`1.0`)으로 복원:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.services.yml \
  up -d
```

| 상황 | 권장 값 | 이유 |
|------|---------|------|
| 평소 개발 / e2e 테스트 | `1.0` | 모든 요청 추적 |
| JMeter 대량 트래픽 테스트 | `0.1` | Zipkin 메모리 보호 |
| 운영 환경 | `0.01 ~ 0.1` | 비용·성능 부담 최소화 |

## 트레이스가 안 보일 때 체크리스트

1. Zipkin 컨테이너가 실행 중인지 확인
   ```bash
   docker ps | grep zipkin
   ```

2. 서비스가 Zipkin으로 스팬을 전송하는지 확인 (로그)
   ```bash
   docker logs omc-gateway | grep -i zipkin
   ```

3. Zipkin API로 직접 조회
   ```bash
   curl "http://localhost:19411/api/v2/traces?serviceName=gateway&limit=3" | jq .
   ```

4. `management.tracing.sampling.probability`가 `0`으로 설정되어 있지 않은지 확인

## Sentry

### 개요

Sentry는 **에러 추적 SaaS**다. 서비스에서 예외가 발생하면 Sentry SDK가 스택트레이스·요청 정보를 자동으로 Sentry 서버로 전송하고, 설정된 채널(Slack 등)로 알림을 보낸다.

- Zipkin → "어떤 요청이 얼마나 걸렸나" (성능 분석)
- Sentry → "어떤 에러가 발생했나" (에러 추적)

두 도구는 역할이 다르므로 함께 사용한다.

### 설정 구조

**DSN**: 에러를 어느 Sentry 프로젝트로 보낼지 식별하는 키. `.env`에 저장하고 Git에는 커밋하지 않는다.

```bash
# .env (gitignored)
SENTRY_DSN=https://xxxx@o123.ingest.us.sentry.io/456
```

```yaml
# 각 서비스 application.yml
sentry:
  dsn: ${SENTRY_DSN:}              # 환경변수 없으면 빈 문자열 → Sentry 비활성화
  traces-sample-rate: 0.0          # 트레이싱은 Zipkin이 담당 → Sentry 트레이싱 비활성화
  environment: development
  ignored-exceptions-for-type: org.springframework.web.context.request.async.AsyncRequestNotUsableException
```

> `traces-sample-rate: 0.0`으로 설정한 이유: Sentry 트레이싱(`SentryTracingFilter`)을 활성화하면 모든 요청에 Sentry 트랜잭션이 생성되어 Zipkin과 중복되고 응답 지연이 발생한다.

### 캡처 대상 에러

`GlobalExceptionHandler`에서 아래 세 가지 경우에 Sentry로 이벤트를 전송한다.

| 예외 | HTTP | 전송 방식 | 의미 |
|------|------|-----------|------|
| `Exception` (그 외 모든 예외) | 500 | `captureException(e)` | 예상치 못한 서버 버그 |
| `AccessDeniedException` | 403 | `captureException(e)` | 권한 없는 API 반복 접근 (공격 시도 감지) |
| Gateway 우회 | 403 | `captureEvent(WARNING)` | X-Gateway-Secret 없이 서비스 직접 호출 |

**캡처하지 않는 것** (정상적인 비즈니스 흐름):
- `BusinessException` → 409 중복발급, 404 쿠폰없음, 400 유효성 실패 등

**무시하는 예외**:
- `AsyncRequestNotUsableException` → Prometheus 스크래핑 중 연결 끊김 (노이즈)

### Sentry 대시보드 보는 법

1. https://soldout.sentry.io 접속
2. 좌측 메뉴 **Issues** → 발생한 에러 목록 확인
3. 이슈 클릭 → 스택트레이스, 요청 정보, 발생 횟수 확인
4. 상단 **Environment** 드롭다운 → `development` 또는 `All Envs` 선택

### Issues vs Events

- **Issue**: 동일한 에러를 그룹핑한 단위. 같은 에러가 100번 발생해도 Issue는 1개.
- **Event**: 각 발생 건. Issue 안에서 발생 횟수로 누적된다.
- 이슈 클릭 → **Events** 탭에서 시간대별 발생 이력 확인 가능.

### Slack 알림

Sentry → Settings → Integrations → Slack 에서 연동 설정.

Alert Rule은 두 가지를 구분해서 사용하는 것을 권장한다.

| 알림 유형 | 설정 | 용도 |
|-----------|------|------|
| Issue Alert | 새 Issue 생성 시 즉시 알림 | 처음 보는 에러 탐지 |
| Metric Alert | N분 내 에러 수 임계치 초과 시 알림 | 에러 폭증 탐지 |

알림 채널: `#sentry-error-noti`

### Issues 상태 관리

| 상태 | 의미 |
|------|------|
| **Resolve** | 수정 완료. 동일 에러 재발 시 Regression으로 새 알림 발생 |
| **Archive** | 알고 있는 이슈. 재발해도 알림 없음 |

### DSN 없이 로컬 실행 시

`.env`에 `SENTRY_DSN`이 없으면 Sentry SDK가 자동으로 비활성화된다. 에러는 로그에만 기록되고 Sentry로 전송되지 않는다.
