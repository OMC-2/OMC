# 07. 전체 서비스 흐름

> 기능 구현 전 전체 흐름 파악, SAGA 보상 트랜잭션 설계 시 참조, 이벤트 발행/구독 관계 확인

---

## 아키텍처 변경 이력

### purchase.confirmed 발행 방식: Redis Stream → DB Outbox

**변경 전 (Redis Stream 방식)**

```
Lua 스크립트
  └─ stream:purchase:confirmed XADD (Redis Stream에 이벤트 적재)

PurchaseStreamWorker (100ms 폴링)
  └─ XREADGROUP → Kafka publish: purchase.confirmed
  └─ ACK

문제점
  - Redis 재시작 / AOF 미활성 환경에서 Stream 유실 가능
  - Consumer Group PEL 관리 복잡 (재시작 후 자기 pending 복구, stale pending 인수 로직 필요)
  - Redis와 Kafka 사이에 at-least-once 보장이 Redis 내구성에 종속
```

**변경 후 (DB Outbox 방식)**

```
Lua 스크립트 (XADD 제거 — Redis 8개 키만 조작)
  └─ 선점 성공 시 단일 DB 트랜잭션
       ├─ p_drop_purchase_reservations INSERT
       └─ p_drop_outbox_events INSERT (status=INIT)

DropOutboxPoller (2초 fixedRate, FOR UPDATE SKIP LOCKED)
  └─ p_drop_outbox_events INIT 레코드 → Kafka publish: purchase.confirmed
  └─ 성공: PUBLISHED / 실패: retry_count+1 / MAX_RETRY 초과: FAILED 격리

장점
  - DB 트랜잭션으로 선점 예약 + 이벤트 저장이 원자적으로 묶임
  - Redis 장애가 이벤트 발행에 영향 없음
  - FOR UPDATE SKIP LOCKED으로 다중 인스턴스 중복 발행 방지
  - PEL/ACK/XCLAIM 등 Stream 운영 부담 제거
```

## 1. 드롭 생성 ~ 오픈

```
관리자 POST /admin/drops
→ drop-service: p_drops 저장 (SCHEDULED)

DropStatusScheduler (5초 폴링)
→ startAt 도달 드롭 감지
→ product-service: GET /internal/v1/products/{productId}/inventories/snapshot → totalQuantity 조회
   (장애 시 totalQty 폴백 + drop.open.inventory.fallback 메트릭 기록)
→ p_drops UPDATE status = OPEN (조건부 UPDATE — 멀티 인스턴스 중복 전이 방지)
→ Redis 워밍
   stock:{dropId} SET totalQty
   drop:{dropId}:status SET "OPEN"
   (워밍 실패 시 DB는 OPEN 유지 — HoldExpireScheduler.recoverFromDb()가 다음 주기에 복구)
→ drop.opened 발행
   └── notification-service: 드롭 오픈 알림 발송
```

## 2. 선착순 진입

```
사용자 POST /drops/{id}/purchase
→ Gateway SoldOutCheckFilter: sold_out:{dropId} 플래그 존재 시 즉시 409 반환 (drop-service 호출 없음)
→ Gateway Rate Limiter: dropId 기준 200 req/s 초과 시 즉시 429 반환

→ Lua 원자 처리 (1 round-trip — OPEN 확인·holdTtlSec·productId 조회 통합)
   ├── drop:{dropId}:status 확인 → OPEN 아니면 409 DROP_NOT_OPEN
   ├── hold_ttl:{dropId} 조회 (만료 epoch 계산용)
   ├── product_id:{dropId} 조회 → 없으면 404 DROP_NOT_FOUND
   ├── purchased:{dropId} 확인 → 있으면 409 DUPLICATE
   ├── stock:{dropId} 확인 → 0이면 409 SOLD_OUT
   ├── stock DECR → 0 도달 시 sold_out:{dropId} SET (Gateway 조기 차단용)
   ├── purchased SADD {userId}
   ├── holds ZADD {orderId} {expireEpoch}
   └── queue INCR → queueNumber
   ※ 1,000 req / 재고 100 → 100건만 이 이후 단계 진입

→ DB 트랜잭션 (선점 성공건만)
   ├── p_drop_purchase_reservations INSERT (orderId, dropId, userId, productId, holdExpiresAt, queueNumber)
   └── p_drop_outbox_events INSERT        (eventId, topic=purchase.confirmed, status=INIT, payload)
   ※ 저장 실패 시 Redis 선점 보상 최대 3회 retry (50ms→150ms 백오프)
      전부 실패 시 drop.purchase.compensation.failed CRITICAL 메트릭 발행

→ 202 Accepted (orderId, queueNumber) 즉시 반환

→ DropOutboxPoller (2초 fixedRate, FOR UPDATE SKIP LOCKED)
   → p_drop_outbox_events WHERE status = INIT ORDER BY created_at (배치 100건)
   → Kafka publish: purchase.confirmed
      └── order-service: PENDING_PAYMENT 주문 생성
   → 성공: status = PUBLISHED
   → 실패: retry_count +1, MAX_RETRY(5) 초과 시 status = FAILED 격리
```

## 3. 결제 SAGA (정상 흐름 — Happy Path)

```
사용자 POST /payments (결제 요청)
→ payment-service: 쿠폰 적용 → PG사 결제 요청

PG사 승인 성공
→ payment.completed 발행
   ├── drop-service: ZREM holds (hold 확정)
   ├── product-service: DB 재고 확정 차감
   └── order-service: PAID 전이

→ stock.deducted 발행
   └── order-service: CONFIRMED 전이

→ order.confirmed 발행
   └── notification-service: 구매 완료 알림
```

## 4. 보상 트랜잭션

> 공통 규칙: 재고는 drop-service가 Redis에서 내부 복구.
> 쿠폰은 order-service가 `coupon.restored`를 발행하고 coupon-service가 복구.
> order-service는 재고를 직접 건드리지 않는다.

### 케이스 A — 결제 실패 / 10분 타임아웃

```
[결제 실패 경로] payment.failed 수신
[타임아웃 경로] hold TTL 만료 → drop-service: hold.expired 발행

→ drop-service: ZREM + INCR + SREM (Redis 재고 즉시 복구) — 재고만 담당
→ order-service: payment.failed / hold.expired 수신
   → 주문 CANCELLED 전이
   → coupon.restored 발행
      └── coupon-service: 쿠폰 복구
   → order.cancelled 발행
      └── notification-service: 결제 실패 / 취소 알림
```

### 케이스 B — DB 재고 차감 실패

```
payment.completed 수신
→ product-service: DB 차감 실패 → stock.failed 발행 (구독: drop, payment, order)
   ├── drop-service: ZREM + INCR + SREM (Redis 선점분 복구)
   │     ※ DB는 확정 차감된 적이 없으므로 Redis 선점분만 복구
   ├── payment-service: 자동 환불 → refund.done 발행
   │     └── notification-service: 환불/취소 알림
   └── order-service: 주문 CANCELLED 전이 → coupon.restored 발행
         └── coupon-service: 쿠폰 복구
→ order-service: order.cancelled 발행
   └── notification-service: 취소 알림
```

### 케이스 C — 쿠폰 이중 사용 실패

```
쿠폰 검증/사용 실패는 payment-service의 결제 트랜잭션 내부에서 발생
(쿠폰 적용 시점이 "결제 요청 직전"이므로 별도 경로를 타지 않음)

→ payment-service: payment.failed 발행 (failureReason = COUPON_*)
→ 이후 케이스 A와 완전히 동일하게 수렴
   ├── drop-service: Redis 재고 즉시 복구
   └── order-service: CANCELLED → coupon.restored 발행 → coupon-service 복구
       → order.cancelled 발행 → notification-service: 취소 알림
```

### 케이스 D — 만료 후 결제 (LATE_PAYMENT, ZREM=0)

```
hold TTL 만료로 주문이 이미 CANCELLED 된 뒤, PG 결제가 뒤늦게 완료됨
payment.completed 수신
→ drop-service: ZREM 시도 → 결과 0 감지 (선점 키 이미 만료) → LATE_PAYMENT 판정
   → refund.requested 발행 (발행 주체: drop-service)
      └── payment-service: 자동 환불 → refund.done 발행
→ order-service: payment.completed 수신 시 주문이 종단 상태(CANCELLED)이므로
   PAID 전이하지 않고 no-op (종단 상태 불변성)

※ 재고·쿠폰은 타임아웃(케이스 A) 단계에서 이미 복구됨
```

## 5. 환불 (사용자 직접)

```
사용자 환불 요청 (익일 자정 이내, CONFIRMED 상태)
→ order-service: Redisson 분산 락 + CONFIRMED Double Check
→ REFUND_REQUESTED 상태 전이
→ refund.requested 발행 (발행 주체: order-service)
   └── payment-service: PG사 환불 API 호출 → refund.done 발행
→ order-service: refund.done 수신 → REFUNDED 상태 전이 (종단)
   └── notification-service: 환불 완료 알림 (refund.done 구독)

※ 재고 소멸 (복구 없음) — coupon.restored 미발행
※ 쿠폰 소멸 (복구 없음) — coupon.restored 미발행
※ 종단 상태가 REFUNDED이므로 order.cancelled는 발행하지 않는다
   (환불 완료 알림은 refund.done이 담당)
```

## 6. 드롭 종료

```
DropStatusScheduler (5초 폴링)
→ endAt 도달 드롭 감지
→ Redis status 플래그 DEL (진입 차단 — DB 업데이트보다 먼저 수행해 gap 방지)
→ p_drops UPDATE status = CLOSED (조건부 UPDATE)
→ drop.closed 발행

정산 배치 후
→ stock:{dropId} DEL
→ purchased:{dropId} DEL
→ holds:{dropId} DEL
→ queue:{dropId} DEL
```

## 7. 래플 응모 ~ 추첨 및 당첨자 자동 결제

```
관리자 POST /admin/raffles
→ raffle-service: p_raffles 저장 (SCHEDULED)

raffle-service 자체 스케줄러
→ SCHEDULED → OPEN 전이

사용자 POST /raffles/{id}/enter
→ Redis SADD raffle:{id}:entries {userId} (중복 방지)
→ 결제 서비스 OpenFeign (카드 유효성 가승인 및 빌링키 발급)
→ p_raffle_entries 저장 (billing_key_id 포함)

raffle-service 스케줄러 (endAt 도달)
→ p_raffle_entries 전체 조회
→ Collections.shuffle() 추첨
→ 단일 트랜잭션
   ├── p_raffle_results Bulk UPDATE (WIN/LOSE)
   └── 당첨자(WINNER) 대상 결제 요청 Outbox INSERT

→ raffle.winner.selected 발행
   ├── payment-service: 저장된 빌링키로 자동 결제 진행
   │    ├── 결제 성공 시 payment.completed 발행
   │    └── 결제 실패 시 payment.failed 발행 (잔액 부족 등)
   └── notification-service: 당첨 알림

→ payment.completed 발행 (결제 서비스)
   ├── order-service: CONFIRMED 주문 자동 생성 및 확정
   └── product-service: DB 재고 확정 차감

→ payment.failed 발행 (결제 서비스)
   ├── raffle-service: 당첨 즉시 취소 및 예비 당첨자 추첨 로직 전환
   └── notification-service: 결제 실패에 따른 당첨 취소 알림

→ raffle.loser.notified 발행
   └── notification-service: 낙첨 알림 발송 (결제가 애초에 없으므로 환불 없음)
```

## 8. 배송 전이

```
배송 스케줄러 (Redisson 분산 락 + CONFIRMED Double Check)

INSTANT (드롭)
→ now() > refundable_until (익일 자정 경과)
→ CONFIRMED → SHIPPING → DELIVERED

RAFFLE (래플)
→ now() > confirmed_at + 1시간
→ CONFIRMED → SHIPPING → DELIVERED

→ order.shipped 발행
   └── notification-service: 배송 시작 알림
```

## 9. Hold TTL 만료 폴링

```
HoldExpireScheduler (10초 fixedDelay)
→ SMEMBERS open_drops  ← DB 조회 없이 Redis Set에서 드롭 ID 목록 조회
   └── Set 비었을 때 DB fallback
       ├── findByStatus(OPEN) → open_drops SADD (복구)
       └── findByStatus(CLOSED) 중 holds 남은 드롭도 SADD (재시작 누락 방지)

→ 각 dropId 순회
   → ZRANGEBYSCORE holds:{dropId} 0 now()
   → 만료 orderId 목록 순회
      ├── expire.lua 실행 (ZREM 시도)
      ├── ZREM=1 (만료 승리) → INCR 재고 복구 → hold.expired 발행
      │      └── order-service: 주문 취소 (없으면 no-op)
      └── ZREM=0 (결제가 먼저 확정됨, 스킵)

   → 처리 후 !isOpen() && isHoldsEmpty() 이면
      → open_drops SREM {dropId}  ← CLOSED + holds 소진 시 자동 제거
```

## 전체 이벤트 흐름 요약

```
이벤트                      발행 서비스        → 구독 서비스
──────────────────────────────────────────────────────────────
drop.opened                drop              → notification
drop.closed                drop              → (없음)
purchase.confirmed         drop              → order
hold.expired               drop              → order
payment.completed          payment           → drop, product, order, coupon
payment.failed             payment           → drop, coupon, order
stock.deducted             product           → order
stock.failed               product           → drop, payment, order
order.created              order             → (없음)
order.confirmed            order             → notification
order.cancelled            order             → notification
order.shipped              order             → notification
coupon.restored            order             → coupon, notification
refund.requested           drop / order      → payment
refund.done                payment           → coupon, notification
raffle.winner.selected     raffle            → order, product, notification
raffle.loser.notified      raffle            → payment, notification
coupon.issued              coupon            → notification
coupon.used                coupon            → (없음, 통계용)
```
